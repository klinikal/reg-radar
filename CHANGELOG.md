# Changelog

All notable changes to reg-radar are documented here, grouped by day. Entries are outcome-focused (what changed and why it matters), not a commit-by-commit log — see `git log` for full detail.

## 2026-09-10

**Upgrading no longer stamps a date bound on regulators you were already collecting** — a follow-on to the module work, found by running it against a real install. #48 promised an upgraded install collects exactly what it collected before, and #51 later added a store-time watermark that did not exist when that promise was written. Together they gave every regulator on an existing install a watermark of "now" at first start, which would have silently dropped anything published earlier that had not been collected yet — a feed's remaining backlog, or the window since the last successful run. A regulator that already has collected items was, by definition, already being collected, so it now gets no lower bound; a regulator with no history is still a genuine first enable and still gets its `new_only` watermark.

**The `#67` repair now derives dates the way the collector does** — for items still inside a feed's window. The item's own page and its feed describe the same instant differently (`2026-08-06T10:25:16Z` against `"August 6, 2026 - 11:25"`), so ids computed from them differ, and an item the feed still carries gets re-collected under the adapter's id rather than deduping against the repaired row. The feed's date is not the better one — it has no seconds and no timezone — but it is the one the collector keeps re-deriving, so it wins for anything still in the window. Items outside it are never re-fetched, and keep the page's more precise date.

**Technical reference moved to `wiki/`, README cut from 658 lines to under 120** (#27) — the README had become the only source for several load-bearing facts (the schema location, the export contract, every config file) while also carrying quick-start instructions nobody could find under them. `wiki/` now holds one page per component, config file, CLI subcommand, script and runbook (48 pages), each following a fixed template (purpose, how it works, inputs, outputs, how to run, how to test, boundaries) with a `sources:` field naming exactly what it was written from. `scripts/check-wiki.py`, adapted from the same pattern already proven in another repo, enforces that every file under `regradar/`, `collector/`, `mcpserver/`, `webui/` and `scripts/` is named by some page, every link resolves, and every page carries the required structure — it fails the build otherwise. `docs/` (the v2 design draft, per-issue build notes, and now-superseded planning history) is dropped from git entirely rather than migrated: it was private planning material, not reference documentation, and shouldn't have been published with the code. The one thing it held that code actually loads, `document-v1.json`, moves to `regradar/schema/` instead of disappearing with the rest. Roughly fifty code comments that pointed at now-removed `docs/issues/NN-*.md` files are repointed at the wiki page that now covers that topic, or dropped where nothing replaced them.

**FCA news and warnings now carry real publication dates** (#67) — they never had. Both feeds render their date for humans (`Thursday, September 3, 2026 - 10:35`), which feedparser cannot read as RFC 822, and the RSS adapter only ever looked at the parsed field — so every item from the UK's primary regulator was dated by when the collector happened to see it. Checked across every enabled feed: 2 of 54 affected, both FCA, so this is that site's date format rather than a general problem. The adapter now falls back to the raw string, through the same text-date parser the scrape adapter uses — promoted to `collector/adapters/base.py` so there is one parser rather than two that can drift, keeping the day-first handling for European `DD/MM/YYYY` and the exemption that stops it corrupting ISO text. Because `make_item_id` hashes the publication date, that fix alone would have inserted a second copy of every affected item rather than updating it, so `scripts/repair_undated_rss_items.py` repairs the existing rows in place: it fetches each item's own page, takes the date the page itself states, recomputes the id and moves the row along with its classifications, artefacts, chunks and search-index entry. Deleting and re-collecting was not an option — each feed holds 20 items, so most affected rows are long out of the window and would have been lost rather than refreshed. The script is a dry run unless given `--apply`, skips rather than overwrites any item already present under the corrected id, and is idempotent. Verified against a copy of a real 21,203-item database: 159 items repaired, none created or lost, 237 classifications followed their items, no orphans, integrity check clean — and the corrected dates reach back to November 2022, where the fetch-time dates began in July 2026.

**A freshness threshold that cannot fire is now a config error, not a quiet no-op** — FATF's grey-list watch shipped with `warn 200 / error 550`, sized carefully against its three-plenary-a-year cadence, and asserted nothing at all: a `page_watch` item carries a fetch-time date rather than the source's, so the age the check reads is always zero days. It looked like the question had been considered and answered, on the one source whose entire purpose is catching a grey-list change. Two things close it. The freshness check now ignores inferred dates, which its own docstring always claimed it did but its filter did not — so a collector-invented date can no longer make a source look fresh. And registry validation rejects `staleness:` on a `page_watch` source outright, along with a `warn_days` above `error_days`, so the shape cannot be written again. FATF's dead override is replaced by a note saying plainly that its freshness is unasserted and why. Being explicit about the limit: this check reads the dates a source supplies, from a single live fetch, so it answers "is this source still publishing?" — answering "has this page changed lately?" needs collection history, and the nightly check has no database by design, since it runs in CI.

**`jurisdiction_type` no longer has two names for one thing** — `non_eea` and `national` were synonyms: both meant "a national competent authority outside the EEA", and the registry used one for the UK and Singapore and the other for the US and the UAE. `non_eea` is retired and its seven entries move to `national`. `member_state` and `eea_non_eu` stay, because those name genuinely different relationships to EU law — it applies directly, versus applying once incorporated into the EEA Agreement — rather than being another word for national. The field is display-only and unvalidated, and existing database rows refresh themselves on the next collection run, so nothing needs migrating.

**`reg-radar setup` and `reg-radar modules`** (#52) — the commands the README and the web UI had started referring to now exist. `setup` walks you through choosing jurisdictions and regulators and writes `config/modules.yaml`; `modules list`, `enable` and `disable` adjust it afterwards. Two things it insists on saying out loud. First, **how much this will actually collect**, before it writes anything — drawn from the volume figures sources declare, and always split into what is known from what isn't rather than quietly treating an undeclared source as small; in this registry most sources declare nothing, so "unknown" is the honest majority. Second, **that turning a module off is not free to reverse**: nothing is collected while it is off, and where a source declares it cannot be backfilled, disabling it names that source and says the gap will be permanent — at the moment of the decision, not afterwards. Asking for a backfill a source cannot give refuses and writes nothing at all. Every proposed file is validated by the collector's own loader before replacing the real one, so the CLI cannot write something the collector would reject at startup, and the previous version is always kept as `modules.yaml.bak`.

**Turning a module on now means something specific** (#51) — `on_enable` was validated but inert; it now decides how much history arrives when you enable a regulator. All three values work through one mechanism: a watermark recorded once, at the moment a module transitions into enabled, and never advanced afterwards. `new_only` (the default, and what a regulator with no module block gets) sets it to the enable moment, which is what turns MAS's 7,412-document first run into nothing at all; `backfill_from` sets it to a date you give; `backfill_all` sets no bound. It is consulted once, so editing `on_enable:` later cannot retroactively re-cut history you already have, and a failed first run leaves the watermark at the enable moment rather than at whatever a partial fetch happened to see — so the retry loses nothing. Worth being precise about what a backfill does here: it lifts the filter, it does not walk an archive. Only the scripts under `scripts/` do that, so enabling one now logs which script actually fetches the history, or says plainly that there isn't one. **`page_watch` sources needed their own answer**, having no history to fetch — their entire state is a hash of a watched fragment. A first observation now establishes a baseline and writes no item, saying so in the log rather than reporting a change that never happened. Baselines survive being disabled, so re-enabling reports a real change if the page moved while you were away and nothing if it didn't. A page whose fragment has gone missing leaves the baseline untouched: an unreadable page is not evidence that the page changed. An existing install with watch history but no baseline adopts its last recorded item, so the first run after upgrading neither swallows a real change nor invents one. Disabling a module stays non-destructive throughout — items, bodies, classifications and baselines all remain.

**The web UI explains what it is and isn't collecting** (#53) — with the registry now holding 62 regulators while a typical install selects only the EEA and the UK, "no results" had become genuinely ambiguous, and a brand-new install with no `config/modules.yaml` sees that state on first load. An empty result now says which of four things is true: this install is not collecting anything yet, no module is enabled for the regulators you asked about (naming them, and how to enable them), those regulators are disabled in the registry itself (so your configuration is right and there is nothing for you to change), or your filters simply match nothing — in which case it also tells you the date this install's history actually starts, so a short backlog does not read as a broken source. A new `/modules` view shows every regulator in the catalogue split into collecting, registry-disabled and not selected, with cadence, next run and item counts. Fixing this surfaced a related bug: the regulator picker was built from the database rather than the registry, so the regulators an install had *never* collected could not be selected at all — precisely the ones a user needs to find in order to turn them on.

**Sources now declare whether they can be backfilled at all** (#50) — turning a module on later only recovers history if the source can actually be paged backwards, and until now nothing in the registry said so. The retention picture is genuinely uneven and the consequences are not recoverable: the OCC's feeds retain ten items, so a source switched off for a week has permanently lost that week, while MAS's Solr index and the Federal Register API both page deeply. Two optional per-source fields record it — `backfill:` (whether it is supported, by what method, and by which script) and `volume_estimate:` (what a first run would produce, and how much arrives per week, each stamped with the date it was measured). **Asking for a backfill a source cannot give you is now a hard error at the moment you ask**, before anything is written, naming the source, why, and what you can have instead: *"us-occ/news does not support backfill: the feed retains only the 10 most recent items, so there is no history to fetch. Use on_enable: new_only — you will get everything published from now on."* A silent no-op, or ten items reported as a successful full-history fetch, is the failure this exists to prevent. A source with no declaration resolves to unsupported — the safe default, since asserting a backfill nobody verified is the same failure wearing a different hat — and figures are declared only where they were actually counted, never guessed. The FCA's counts keep their real `as_of` of 2026-07-02 rather than today's date, because stamping them today would assert a verification that never happened.

**UAE onshore: VARA and the CBUAE rulebook** (#45) — Dubai's Virtual Assets Regulatory Authority under its own `ae-dubai` jurisdiction, a flat sibling of the two free zones rather than their parent: the free zones are carved out of emirate law as well as federal law, so an `ae-dubai → ae-difc` edge would have pushed VARA rulebook changes at DFSA-regulated firms. VARA contributes news, regulatory notices and rulebook revisions, plus a page watch on its public register, which has no feed of any kind. CBUAE is covered through `rulebook.centralbank.ae` — that host answered plain HTTP with no challenge at all, so no FlareSolverr is needed, while `www.centralbank.ae` sits behind a managed challenge site-wide and is left unconfigured rather than guessed at. The VARA rulebook URL carried an elided chapter list in the planning notes; the twelve real chapter ids are enumerated in full, since the abbreviated form would have silently returned nothing. Two things checked rather than assumed, after the ADGM date problem: VARA's `<time datetime>` really is the date the page displays, not a hidden last-edit stamp, and CBUAE's only date is a parenthesised *effective* date whose newest value is in the future — so CBUAE items carry no asserted publication date at all. One citation remains **unverified**: the SCA decision number survives only as an alias drawn from secondary sources, because `sca.gov.ae` is JavaScript-only and the federal legislation portal refuses non-browser clients. It is marked as such in the taxonomy. `config/taxonomy.yaml` goes to version 3 with twelve UAE instruments.

**US state coverage: NYDFS, California DFPI and NMLS** (#44) — three bodies, deliberately not fifty. New York's DFS is the state regulator whose crypto rules firms elsewhere actually read, and contributes its newsroom, industry letters and enforcement tables plus a page watch on the virtual-currency licensee hub. California's DFPI is the only other state with a machine-readable feed and an active crypto docket. CSBS's NMLS `State Licensing` feed is a national aggregator of state licensing developments maintained by state-regulator staff — one anonymous endpoint covering all fifty states — so it sits under `us` rather than any single state; building 49 scrapers to rediscover what it already publishes is work not worth doing. Texas DOB (an RSS feed with a valid envelope and zero items), Florida OFR and Wyoming were checked and rejected, and NASAA is hard geo-blocked outside the US and remains unverified.

This one also fixed a bug in shared code that predates it. `scrape.py` applied day-first parsing to *any* date read as text, which does not leave an ISO date alone: `2026-08-03` became 8 March and `2026-12-01` became 12 January, stored with `date_inferred: false` — asserted as fact rather than guessed. Every enabled scrape source was checked and only the two new NYDFS tables were affected, because existing sources either carry a `<time datetime>` attribute or render dates in a non-ISO format — so it was latent, and NYDFS is simply the first source to render dates that way. The fix keys off the string's shape rather than a per-source flag, so European `02/07/2026` still reads as 2 July. Two adapter capabilities landed alongside: per-source request headers (NMLS's SharePoint list serves Atom XML rather than JSON without an explicit `Accept`, and `$format=json` does not override it) and `url_field: null` with a `landing_url`, for an API whose items carry no URL of any kind.

**UAE free zones: DFSA and ADGM FSRA** (#43) — the DIFC and Abu Dhabi Global Market, modelled as `ae-difc` and `ae-adgm` under an onshore `ae` they are constitutionally carved out of. Only the financial-services acquis is disapplied in a free zone — federal AML/CFT law still bites — so they are children rather than siblings, and over-inclusion runs upward, which is the safe direction. Both regulators' rulebook updates come from Thomson Reuters-hosted mirrors, and for DFSA that is not a convenience: its own site returns a deterministic Cloudflare 403 on `/alerts`, `/rulebook` and `/public-register` while serving `/news` and `/rss` at 200 in the same second, so the mirror is the only route in. DFSA's news feed carries a widened staleness threshold — its own history contains a 792-day gap, so the default would page on entirely normal behaviour. **ADGM's announcements source ships disabled, because the planning assumption behind it turned out to be false.** `adgm.com`'s sitemap `lastmod` is a last-edit timestamp, not a publication date: of twelve announcements checked against the date printed in each page's own body, only three matched, and 660 of the 1,113 share a single CMS-migration stamp while their real dates span 2016–2024. The sitemap adapter treats a parsed `lastmod` as an asserted publication date, so those items would drive export paths, digests, recency queries and the freshness check from dates that are wrong — confidently wrong being worse than unknown. The entry and its fixture are merged so re-enabling is one line once the real date is recovered from the page body.

**US enforcement and press scrapes: Treasury and FINRA** (#42) — neither publishes a usable feed. Treasury has no RSS anywhere on its site, and `finra.org/rss.xml` is a dead Drupal default: HTTP 200, well-formed, ten items, newest from **July 2020**, which would have looked permanently healthy while collecting nothing. Both are scraped instead: Treasury's press releases, FINRA's news releases, and FINRA's monthly disciplinary-action reports. FINRA is the registry's only `jurisdiction_type: sro` — a private self-regulatory organisation, not a government agency, whose rule changes take effect only once filed with and approved by the SEC, which is why those already arrive via the Federal Register. **Every selector was derived from live HTML**; the ones carried in the planning work were guesses and all but one were wrong. The disciplinary-actions URL was wrong too, and interestingly so: the page named in planning is real, 95KB, server-rendered — and a *search form*, with no table, no rows and no dates. Its selectors would have parsed to zero items on a large body, which is precisely the shape the new block detection records as `blocked`, permanently. The actual listing lives at a different path and is what ships. **SEC litigation releases are not included:** they exist only as HTML, and `www.sec.gov`'s HTML path answers a 1,925-byte 403 rate-limit page from this network — identical under a full browser user agent, while the RSS path returns 200 in the same sequence. Rather than ship unverified selectors, that source is left out and needs re-attempting from a different network.

**Fixed: a misconfigured install could collect nothing and still report success** (#39) — found while shipping FATF, which collects only through FlareSolverr. A regulator marked `cloudflare_protected` with no `FLARESOLVERR_URL` set was skipped before any fetch was attempted: nothing recorded, no counter moved, and the run still finished `success` with a single warning in the log. That is exactly the invisible failure the source-health work exists to kill, on the one source it was written for — a grey-list change would have been missed behind a green run. Each of the regulator's enabled sources is now recorded as `blocked`, counted, and named in the run summary, so a misconfigured install is as loud as a blocked one.

**FATF, and a standalone `intl` jurisdiction** (#47) — the one international standard-setting body kept from the planning round, covering the black-and-grey lists and the home-page news carousel. The list source is a `page_watch` scoped so the watched fragment carries the actual country lists, which means the diff *is* the substance rather than a signal to go and look. `intl` is deliberately a root with no parent or child edges: FATF Recommendations bind nobody directly — they are transposed into national and supranational law — so modelling FATF as an ancestor of any jurisdiction would assert an applicability that does not exist. All four shipped profiles opt in by naming `intl` explicitly. The grey list is revised at plenary, three times a year, so a ~130-day gap is healthy and the source carries a widened staleness threshold rather than warning on normal cadence. FATF is Cloudflare-protected and collects only with `FLARESOLVERR_URL` set; a live run through FlareSolverr returned 13 items.

**Singapore: MAS and Singapore Statutes Online** (#46) — MAS publishes no RSS anywhere, so all eight MAS sources come from its open, unauthenticated Solr search API: media releases, speeches, consultations, enforcement actions, notices, circulars, guidelines and legislation. Two scoped page watches on Singapore Statutes Online track amendments to the Payment Services Act 2019 and the Financial Services and Markets Act 2022, filed under a separate `sg-sso` entry because the statute publisher is the Attorney-General's Chambers, not MAS. Every source was fetched live and every `numFound` matched. Three things this depended on landing first: #37's browser-shaped user agent (a bare UA gets an 853KB decoy page at HTTP 200 instead of JSON), #36's relative-URL resolution (MAS's index has no absolute-URL field at all), and #39's block detection. Two traps are worth recording because they are silent, not loud: the enforcement source must filter on **two** content types — `"Enforcement Actions"` alone returns 55 of 137 items and drops the other 82 without a word — and the statute watches must stay scoped to `#docTimeline`, because SSO injects the current date into the page body and a whole-page watch would report a change every day forever. MAS Notices are classified `legislation`: they are binding statutory directions, and no new `notice` document type was created because "notice" is already claimed in this corpus by `enforcement` (the FCA's and MFSA's notices are enforcement paperwork). `regulations_and_legislation` ships with a widened staleness threshold — its newest item is 374 days old, which is genuine episodic cadence rather than a broken feed, with a ~460-day gap in its real history.

**Per-module poll cadence** (#49) — the `schedule:` key #48 validated but ignored now does something. Each distinct cron expression across your selected modules gets its own scheduler job, so a source that needs watching every four hours can have that without putting every other regulator on the same footing. It exists because retention varies: the OCC's feeds hold ten items, so a source polled too slowly loses documents permanently, while the FATF grey list changes about three times a year and a daily poll is pure noise. Sources with no `schedule:` are unaffected and still run on the global `SCHEDULE` as a single job, byte for byte as before — asserted by a test, because silently changing the default cadence would undo #48's no-behaviour-change guarantee. Overlapping runs were already prevented by a single collector lock and still are; the cadence groups are disjoint by construction, and a job that finds the lock held now logs which cron expression and which regulators it skipped rather than failing quietly. A `--once` run ignores cadence entirely and collects every selected module, as before.

**US federal news, enforcement and speeches** (#41) — five more US entries alongside #40's Federal Register: the SEC, CFTC, Federal Reserve, OCC and CFPB, 16 enabled RSS sources between them, covering the press releases, enforcement actions, supervisory bulletins and speeches that the Federal Register does not carry. All verified live on 2026-09-10, every item with a real publication date — including the Federal Reserve's feeds, whose CDATA-wrapped dates parse correctly. Two sources ship deliberately **disabled** rather than given a widened staleness threshold: `us-cfpb/enforcement_actions` (healthy feed, newest item 2025-09-22 — the documented CFPB enforcement dormancy) and `us-sec/testimony` (episodic congressional testimony, newest item 210 days old at capture). Both would otherwise trip #39's freshness assertion, and raising the threshold to silence them would hide a genuinely dead feed later; their fixtures are kept so re-enabling is a one-line change. FDIC is **not** included: its only feed is third-party GovDelivery (`www.fdic.gov/rss` is a 404) and 900KB of its 909KB response is email-template table markup that the RSS adapter would store as each item's body. It needs a way to ignore a feed's description body before it can ship. As with all US coverage, nothing here is collected unless selected in `config/modules.yaml`.

**First US coverage: the Federal Register** (#40) — one unauthenticated API call now covers rulemaking and notices for seven federal agencies (SEC, CFTC, FinCEN, OCC, the Federal Reserve, FDIC and the CFPB) plus FINRA rule filings, which reach the Federal Register as SEC "Self-Regulatory Organizations; …" notices. A live run returned 200 items spanning 24 days, every one with a real publication date. Known limitation, recorded in the entry: all of it lands under a single `us-federal-register` regulator id — the per-item `agencies` field is fetched, but no adapter can yet attribute one source's items to several regulators. Worth knowing what this source does *not* carry: no enforcement, litigation, press releases, speeches or testimony, which is why those need sources of their own. The Treasury slug is deliberately excluded because it co-lists IRS, OFAC, TTB and Mint documents — 37 of 75 Treasury hits in a 30-day window were IRS. **No existing install starts collecting this**: the `eu/*` + `gb/*` module selection written at upgrade excludes it, which is asserted by a test that now also fails if a future non-EEA entry leaks into an upgraded install's set.

**Blocked sources now fail loudly, and stale ones get called out** (#39) — the most operationally important gap this expansion exposed: a source can report perfectly healthy while being useless, and until now the collector could not tell. A WAF block, an unsolved bot challenge or a decoy page all arrive as "no new items today", indistinguishable from a genuinely quiet regulator. The fetch layer now classifies responses before they reach a parser, on five signatures — a `cf-mitigated: challenge` header, an `x-sucuri-block` header (`GEO02` is a geo-block no workaround fixes), `server: cloudflare` on a non-200, Cloudflare/Sucuri interstitial markers in a 200 body, and a large response body that parses to zero items, which is the shape of MAS's 853KB decoy. Classification happens **before** parsing on purpose: a challenge page that happens to match a source's selectors would otherwise write garbage into the corpus, which is worse than collecting nothing. `blocked` is a distinct source state recorded alongside — never replacing — the existing error and empty-run counters, and it surfaces in the run summary, the web UI's source-health view, the `get_health_tool` MCP response, and the webhook and digest paths. Those last two previously returned early when there was nothing new to send, which is exactly what a blocked source looks like; they now deliver on either signal, and a blocked-only delivery deliberately does not advance the subscriber's cursor. Separately, the nightly source-health run now asserts freshness as well as HTTP status: a source whose newest item is over 90 days old warns, over 365 days errors, overridable per source with a `staleness:` block for genuinely low-cadence publishers like the FATF grey list. Every workaround this expansion adds depends on failing visibly when it stops working — a compliance tool's value collapses the moment it quietly stops watching something its user believes it is watching.

**Browser-shaped user agent, and throttling for sec.gov** (#37) — the default `USER_AGENT` becomes `Mozilla/5.0 (compatible; reg-radar/2.0; +https://github.com/klinikal/reg-radar)`: browser-shaped, but still honest and attributable — it names no specific browser version and keeps the project URL so a site operator can identify and contact the crawler. Several hosts the coverage expansion needs treat a bare tool UA as a bot, and the dangerous case is silent: MAS answers a non-browser UA with **HTTP 200 and an 853,817-byte "Maintenance" page** instead of its real JSON, so `raise_for_status()` sees nothing wrong and the collector would report healthy runs while collecting nothing, indefinitely. Requests to `sec.gov` and its subdomains are now spaced at least a second apart — SEC's published Fair Access policy asks only for a contact string, but observed behaviour is stricter, and a burst of about eight rapid requests earns a site-wide penalty box lasting minutes. The user-agent string had been copied into eight places and had already drifted; it is now defined once, in `collector/adapters/http.py`, and the `USER_AGENT` overrides baked into `Dockerfile.collector` and the nightly source-health workflow are **removed** rather than updated — they silently shadowed the code default, which is how a change like this comes to be inert in production. **Upgrading an existing install: if your `.env` sets `USER_AGENT`, update it, or your install keeps the old blocked value.** Verified against all 33 enabled regulators / 63 enabled sources before and after, item counts unchanged at 62 of 63; the exception was a transient TLS handshake timeout at `afm.nl` that reproduces under both user agents.

**Modules: choose what this install collects** (#48) — `config/regulators/` stays a complete catalogue; `config/modules.yaml` (yours, gitignored, with a committed `config/modules.example.yaml` alongside it in the `.env` / `.env.example` pattern) is your selection from it. A module is a regulator; a jurisdiction wildcard like `eu/*` expands to that jurisdiction and every descendant of it, so `eu/*` covers ESMA and every member state's authority. Resolution runs `defaults` → jurisdiction wildcard → explicit module id → `sources:`, narrower always winning, and the registry wins on `false` — anything `config/regulators/` marks `enabled: false` is never collected however explicitly you selected it, logged as a `WARNING` naming the module and source when it overrides something you asked for by name. Three loader states: a `modules.yaml` collects exactly what it selects; no file plus `REGRADAR_COLLECT_ALL=true` collects the whole registry; no file and no env var collects nothing and says so in one line, exiting 0 rather than looking like a crash. An invalid file (bad cron, unknown module id, unknown source label) is refused at startup with the offending entry named. `schedule:` and `on_enable:` are validated and carried through the schema but not yet acted on — the collector still runs one global `SCHEDULE`. **Existing installs need do nothing:** the first run after upgrading writes a `modules.yaml` containing `eu/*` and `gb/*`, which resolves to exactly the 33 regulators / 63 sources collected before — asserted against the real registry by `tests/test_modules.py`. What this buys is the thing the global coverage expansion would otherwise break: an EEA-only operator does not start downloading MAS circulars and NYDFS consent orders on their next upgrade. The cost, stated rather than averaged: query-time filtering is free to reverse, collection-time filtering is not — a module that was off for six months leaves a six-month hole, and many sources cannot be backfilled.

**Local upgrade from casp-radar to reg-radar completed** — the documented volume migration (`casp_radar_data` → `reg_radar_data`, backup dir moved to match) plus the v1→v2 data migration (reclassify `document_type`/`instrument` on both source-default and rule paths, legacy `content_tags` imported, `body_md` backfilled from `raw_content` for 18,603 pre-v2 items) were run end to end against the live local install, verified by matching item counts (20,715) before the old volume was deleted. The stale `.env` (still pointing at `casp_radar.db` and the old `regulators.yaml` path) was updated to the current v2 defaults. Found and fixed a gap the README's upgrade steps didn't cover: the volume-copy step preserves the old `casp_radar.db*` filenames, which the new `.env`'s `reg_radar.db` path wouldn't find, so the app would silently start against a fresh empty database — the DB files now get renamed inside the volume as an explicit step before first boot on the new volume. Local project folder renamed `casp-radar` → `reg-radar`; git worktree metadata repaired for the one active worktree (`v2`) that survived the move.

**Renamed casp-radar to regradar** (#3) — code-side rename only; no functional change. The database file (`casp_radar.db` → `regradar.db`), Docker volume (`casp_radar_data` → `regradar_data`), Litestream backup path, compose project name, default `USER_AGENT`, MCP server name, and the `skills/casp-radar-*` directories all move to the `regradar` name. Python packages (`collector`, `mcpserver`, `webui`), database tables, and the item id scheme are unchanged. Existing installs: see the README's "Upgrading from casp-radar" section for the volume migration steps — the compose file also accepts `DATA_VOLUME_NAME=casp_radar_data` as a stopgap so nobody boots against an empty database by surprise. The GitHub repository rename, name/trademark check, and the `2.0.0-alpha.1` tag are tracked separately and not part of this change.

**Canonical document format and original artefacts** (#4) — every item now has one canonical shape: a YAML-frontmatter Markdown document (id, title, source URL, regulator, jurisdiction and its ancestors, dates, labels, provenance, content hash) with the extracted body as Markdown, validated against a published JSON Schema in `regradar/schema/`. `reg-radar render` writes that layout to disk, so the corpus can be dropped straight into a document management system or a note-taking vault without a bespoke exporter. The original fetched artefact (the HTML page or PDF as served) is stored alongside it under `ARTEFACTS_DIR` with its mime type and sha256, so a better extractor — or a legal team wanting the actual PDF — never has to re-fetch from the regulator. `scripts/reprocess_bodies.py --from-raw-content` re-derives Markdown bodies for items collected before this landed.

**Taxonomy, jurisdictions and a classification store with provenance** (#5) — flat tag lists are replaced by a configurable taxonomy (`config/taxonomy.yaml`): named axes, each with a cardinality and a controlled vocabulary of values with aliases and a per-axis minimum confidence. `document_type` (single-valued) and `instrument` (multi-valued) ship; the code hard-codes no axis name except `jurisdiction`, so adding one is a config change. Jurisdictions (`config/jurisdictions.yaml`) became a hierarchy with lower-case ids: every EU member state lists `eu` as a parent, so a filter on `fr` returns AMF *and* ESMA, and `UK` became `gb`. Labels are no longer written onto the item — every classification is a row recording who said it (`by`), how sure they were (`confidence`) and which taxonomy version was in force, with the highest-confidence live row above the threshold winning. A human correction is never overwritten by an automated pass. `reg-radar reclassify` re-applies source defaults or re-scores against the current config, and supersedes rows the config no longer supports rather than leaving them live. `get_taxonomy_tool` and `list_labels_tool` expose the vocabulary and what is actually in use.

**Rules engine, classification write interface and a classifier skill** (#6) — `config/rules.yaml` replaces v1's keyword alerts with a deterministic weighted rules engine: each entry scores one (axis, value) pair from regex matches across chosen fields, with a title multiplier and a global minimum confidence, and runs on every newly collected item. `/alerts` in the web UI became `/rules`, backed by that file, with validation against the taxonomy on save (`/alerts` redirects). The write side is now a real interface: `classify_item_tool`, `classify_items_tool` (up to 100 at once, every entry validated before anything is written, per-entry errors returned), `get_unclassified_tool` for paging the backlog one axis at a time, and `POST /api/items/{id}/classifications` for human corrections. `skills/regradar-classifier/` documents the loop so any MCP-connected agent can work the backlog — the repository holds no API keys and picks no vendor. `scripts/eval_classifier.py` scores live labels against a hand-labelled gold sample so accuracy is measured, not assumed.

**Profiles and activities** (#7) — a profile is a saved, named filter: jurisdictions (with `eu/*` selecting the EU and every member state), activities, instruments, excluded instruments, document types, regulators and languages, plus `include_unclassified` so items nothing has labelled yet stay visible by default. Activities (`config/activities.yaml`) let a profile say "I am a CASP" instead of listing instruments. The same profile applies identically in the web UI's picker, every MCP query tool's `profile` parameter, the JSON API, the exporter, the Atom feeds, webhooks and digests — one definition, one behaviour. Four templates ship in `config/profiles/`: `eu-casp`, `eu-bank`, `eu-emi`, `uk-equities-dealer`; your own profile is a YAML file passed by path.

**Source health, fixtures and nightly contract tests** (#9) — the failure that used to go unnoticed for weeks was a source returning HTTP 200 with markup the parser no longer matches. Every enabled source now has a captured last-known-good response under `tests/fixtures/sources/` and an offline contract test asserting the parser still produces the same shape from it. A nightly workflow re-fetches each source live, compares it against the fixture, and files (or closes) a GitHub issue per source, so selector drift surfaces on its own. A stall detector counts consecutive successful-but-empty runs per source, distinct from outright fetch failures, and surfaces stalled sources through `get_health_tool`, `list_regulators_tool` and the web UI's regulator panel. `scripts/capture_fixture.py` re-captures a fixture deliberately; nothing refreshes one automatically.

**Source adapter framework and per-jurisdiction registry split** (#10) — the three hard-coded source types inside one `fetch_source()` became a registry of adapter classes, each owning its own fetch and parse, sharing one post-fetch pipeline (extraction, snippet, language, id generation, artefact storage). Adding a fetch strategy is now a new file, not a new branch in shared code, and `sitemap`, `json_api` and a Playwright-backed `browser` adapter join `rss`/`scrape`/`page_watch`. The single 1,800-line `config/regulators.yaml` split into one file per jurisdiction under `config/regulators/`, validated against `config/jurisdictions.yaml` at startup, so adding a regulator is one config file, one fixture and one test, and a review diff names the jurisdiction it touches.

**Export, changes cursor, outbound feeds and webhooks** (#8) — the one change-stream primitive every downstream adapter now builds on: "everything that changed since cursor X" (an opaque `<updated_at>|<item_id>` cursor, id as tiebreak on equal timestamps). `get_changes_tool` and `GET /api/changes` both read it directly off `updated_at`, so a reclassification or human correction is now visible to a poller, not just a newly fetched item — `get_items_since_tool` is deprecated in favour of it (kept working, logs a warning). `reg-radar export --format markdown|jsonl --out <dir>` writes the canonical document layout (or JSONL), idempotent and cursor-tracked via a `.reg-radar-cursor` file in the output directory, with `--with-originals` to also copy artefacts. `GET /feeds/<profile>.atom` gives any RSS/Atom reader a per-profile feed. `config/webhooks.yaml` (unset by default) defines subscribers that get an HMAC-signed POST of new matching items after every collection run, with per-subscriber cursors, doubling-backoff retries, and a delivery log — one subscriber's failure never blocks another's.

**Published dataset** (#12) — a nightly GitHub Actions workflow publishes the full corpus as a GitHub release: a tarball of the canonical document tree plus `export.jsonl`, a `manifest.json` (schema and taxonomy version, `generated_at`, item count, per-regulator counts, excluded regulators, sha256), a moving `latest` tag and an immutable `dataset-YYYY-MM-DD` one. `reg-radar import-dataset <url|path>` loads it: sha256 verified before anything is written, a non-empty database refused without `--force`, items and classifications loaded straight from `export.jsonl` with their original provenance (`by`, `confidence`, `taxonomy_version`) intact, and a URL download bounded by `--timeout` and `--max-bytes`. What this saves a new install is the **historic backfill scripts** — the slow, FlareSolverr-throttled part — not the routine collection run, which reads each source's current feed pages either way; nothing filters fetches by date. The import records the manifest's `generated_at` as a sync cursor marking where the snapshot ends — a bookmark for change-stream consumers (`get_changes_tool`, `/api/changes`, a webhook subscriber) that want only post-import changes, never applied automatically. `import-dataset` prints it with ready-to-paste commands and `get_health_tool` reports it as `dataset_import`; `reg-radar export` still always writes the whole corpus into a fresh `--out`. Supporting changes: `reg-radar export` gained a repeatable `--format` (markdown and jsonl from one pass over one change set) and `--exclude-regulator-file`. A `NOTICE` file at the repository root records what is known about each enabled regulator's reuse terms — cited and quoted where the regulator states them, "unclear" otherwise, which is not the same as forbidden — and `config/dataset_exclusions.yaml` (empty for now) is where a regulator goes if its terms are found to forbid redistribution.

**Digests** (#13) — `config/digests.yaml` (opt-in, unset by default) defines scheduled digests: a profile, a cadence, and one or more delivery channels. Each digest renders everything that changed since its own stored cursor, grouped by jurisdiction then regulator, as plain text and HTML, and delivers by email (SMTP, with STARTTLS certificate and hostname verification), Telegram, or an HMAC-signed webhook. A digest's cursor advances only if every one of its channels succeeded, so a failed send is retried in full rather than silently skipped. The collector's own scheduler runs them — there is no second cron to configure — and `reg-radar digest --preview --profile <p>` renders one to stdout without sending anything, while `reg-radar digest --send --name <n>` can be driven from external cron instead.

**Batch classifier runner** (#14) — `reg-radar classify --provider <p> [--axis <a>] [--limit N]` works through the unclassified backlog without an agent in the loop. Providers are pluggable and their SDKs import lazily, so nothing is installed for a provider you don't use; the `command` provider shells out to any CLI that reads a prompt on stdin and writes text on stdout, which lets a subscription-backed tool drive classification instead of a metered key (check that vendor's terms before using it unattended). Every write carries `by: llm:<provider>/<model>` provenance, `--dry-run` classifies and prints without writing anything, and metered providers log token counts and an estimated cost per call priced from `config/llm_prices.yaml`; unmetered ones log as unmetered rather than fabricating a figure.

**Narrowed `document_type` source defaults to single-purpose feeds** — audited every `labels:` block across all 44 regulators in `config/regulators/*.yaml`. The v1→v2 tags migration (§4.7) had stamped `document_type: warning` at confidence 1.0 onto general/mixed feeds (`all_news`, `announcements`, `market_supervision`, `publications`, `news_and_warnings`, etc.) because v1's `warnings` tag was applied indiscriminately — since a source default at 1.0 outranks any rule or LLM label (§4.4), those mislabels were effectively permanent. Removed the `document_type` default from 26 sources that are not single-purpose for the value they carried, and corrected 4 sources that were single-purpose but mislabelled (e.g. BaFin's `press_pr` feed was tagged `warning` instead of `press_release`; DNB's and FCA's enforcement-notice feeds were tagged `warning` instead of `enforcement`). 12 sources kept their `document_type` default unchanged, where the feed is genuinely single-purpose (a `warnings`/`press_releases` label or equivalent, or a `page_watch` source). Operators should run `reg-radar reclassify --axis document_type` after upgrading to clear the stale `source_default` rows and let items fall back to rules/LLM classification.

**Fixes found against the real database** — bugs that only appeared once the whole pipeline ran over the live corpus rather than test fixtures. Classification writes stored `updated_at` in a different string format from the ORM's own writes, so the change cursor compared the two as text and could stop advancing, silently starving every change-stream consumer. `reg-radar reclassify` left rows live when the config no longer supported them, so a removed source default stayed as an effective label forever; it now supersedes them. Exports dropped `jurisdiction_ancestors` and `label_provenance` from every document, and wrote an empty body for any item collected before `body_md` existed — both are now derived on the export path, so a v1-upgraded database exports real text. The regulator-labels migration also now always runs its database jurisdiction rewrite, rather than skipping it when the YAML had nothing left to migrate.

**Final review fixes** — the whole-branch review before merge, applied in one pass. The README's volume-migration steps could destroy a live database if both options were followed in order: the old volume is now deleted only after the migration is verified, and the `DATA_VOLUME_NAME` override is removed explicitly first. Taxonomy and activities load at process startup, so a broken config kills the container at boot instead of turning every request into a 500. A `jurisdictions` filter passed without a taxonomy now raises instead of silently widening the query to the whole corpus. `/api/changes` and `reg-radar digest --preview` pass the taxonomy through, so their documents carry `jurisdiction_ancestors` and `label_provenance` like every other surface. `get_unclassified` derives bodies for v1-upgraded rows, so a classifier is not handed empty text. Classification writes against an item id that does not exist are rejected instead of recording an orphan row. The regulator panel takes country names from `config/jurisdictions.yaml` rather than a stale hand-maintained map, restoring search-by-country. Email delivery verifies the TLS certificate and hostname on STARTTLS. A webhook delivery failure can no longer make `--once` exit non-zero. The exporter reports only the items it actually wrote and warns about unparseable snapshot lines instead of dropping them quietly.

**Renamed regradar to reg-radar** — final naming pass: the interim name used throughout the v2 build (`regradar`) becomes the hyphenated **reg-radar** everywhere user-facing (Docker/compose project and volume names, the DB file, the MCP server name, the console script, the webhook signature header, the export cursor filename, dataset release/tarball names, skills directories, and docs). The Python package stays `regradar` (hyphens aren't valid in a module name) — `python -m regradar.cli`, `regradar/`, database table/column names, and the `regradar_schema` frontmatter key are unchanged. A `2.0.0-alpha.1` tag follows the merge of this change.

## 2026-07-04

**Historic backfill migrated to the new source/content tag split** — ran the migration script (built and dry-run tested yesterday) against the live database: 12,963 legacy items had their `source_tags` re-derived from the old `tags` column (blanket `casp`/`mica`/`aml`/`art`/`emt`/`dora` labels stripped) and `content_tags` freshly computed by re-running the keyword matcher against each item's real text — 600 items picked up a genuine, evidence-based content tag as a result. The final review of this migration script (before today's run) caught a Critical bug that would have silently wiped `source_tags` on every row the new collector had already tagged correctly — fixed and re-verified before the real run.

**MCP server security/correctness audit** — a full external review of `mcpserver/` produced 9 security/correctness findings and 7 improvement opportunities, all implemented:
- Fixed a timestamp-format bug in `get_warnings` that silently dropped items published on the cutoff day itself.
- Floored `limit` clamps across `search_items`, `get_recent`, and `get_run_log` — a negative limit could previously disable SQLite's `LIMIT` entirely, returning the whole table.
- Added a `limit` to `get_warnings` (previously unbounded) and offset-based pagination to `search_items`.
- Fixed `search_items` to use AND search semantics for multi-word queries (it was treating them as one exact phrase).
- The MCP server now opens the database read-only and fails fast if the database file is missing, instead of silently creating an empty schema.
- Enabled DNS-rebinding protection on the HTTP transport (FastMCP doesn't enable this automatically when binding `0.0.0.0`).
- Tool errors are now sanitized before reaching MCP clients — internal details (DB paths, SQL text) no longer leak into error messages.
- Fixed `Optional` type annotations across tool signatures.
- Five new MCP tools: `count_items_tool`, `get_month_facets_tool`, `list_tags_tool`, `get_items_since_tool` (a polling primitive), `get_health_tool` (collector freshness/readiness).
- All 11 tools now return structured content (dicts/lists) instead of JSON-encoded strings; `get_item_tool` gained a `max_content_chars` option to protect agent context windows.

**Production database corruption incident** — live testing surfaced real SQLite corruption in the `items` table (not the FTS search index, as first suspected). Root cause: the database very likely lived on a macOS Docker Desktop bind-mount, a known corruption risk for SQLite's WAL-mode locking. Recovery was attempted (an initial "fully recoverable" estimate didn't hold up under independent re-verification — the real number was ~83%), and the decision was made to scratch the corrupted database and let the collector rebuild it fresh, given the data is cheaply re-collected from public RSS/scrape sources.

**Infrastructure hardening**, shipped the same day to prevent a repeat:
- Moved the database off the macOS bind-mount onto a genuine Docker-managed named volume.
- Added Litestream as a continuous-backup sidecar, streaming the live database to a plain folder on the host disk — restore path verified end-to-end, not just configured.
- The collector now runs a full integrity check (`PRAGMA integrity_check`) at the start of every collection cycle and surfaces the result loudly through `get_health_tool`'s new `db_integrity` field, instead of corruption sitting silently undetected until a search happened to fail.
- Fixed a live regression the DNS-rebinding fix introduced: operators who remap the MCP server's published port (a documented workaround for port conflicts) got every request rejected with a 421 — the allowed-hosts list is now extensible via `MCP_EXTRA_ALLOWED_HOSTS`.
- Fixed `docker-compose.yml`: the `mcp` and `webui` services had never actually loaded `.env` — only `collector` had, so any environment-variable configuration for the other two services was silently a no-op.
- Fixed a dependency version conflict (`httpx`/`uvicorn` pins one version below what `mcp` requires) that blocked installing all three services' dependencies together for local testing.
