# Changelog

All notable changes to reg-radar are documented here, grouped by day. Entries are outcome-focused (what changed and why it matters), not a commit-by-commit log — see `git log` for full detail.

## 2026-09-10

**Browser-shaped user agent, and throttling for sec.gov** (#37) — the default `USER_AGENT` becomes `Mozilla/5.0 (compatible; reg-radar/2.0; +https://github.com/klinikal/reg-radar)`: browser-shaped, but still honest and attributable — it names no specific browser version and keeps the project URL so a site operator can identify and contact the crawler. Several hosts the coverage expansion needs treat a bare tool UA as a bot, and the dangerous case is silent: MAS answers a non-browser UA with **HTTP 200 and an 853,817-byte "Maintenance" page** instead of its real JSON, so `raise_for_status()` sees nothing wrong and the collector would report healthy runs while collecting nothing, indefinitely. Requests to `sec.gov` and its subdomains are now spaced at least a second apart — SEC's published Fair Access policy asks only for a contact string, but observed behaviour is stricter, and a burst of about eight rapid requests earns a site-wide penalty box lasting minutes. The user-agent string had been copied into eight places and had already drifted; it is now defined once, in `collector/adapters/http.py`, and the `USER_AGENT` overrides baked into `Dockerfile.collector` and the nightly source-health workflow are **removed** rather than updated — they silently shadowed the code default, which is how a change like this comes to be inert in production. **Upgrading an existing install: if your `.env` sets `USER_AGENT`, update it, or your install keeps the old blocked value.** Verified against all 33 enabled regulators / 63 enabled sources before and after, item counts unchanged at 62 of 63; the exception was a transient TLS handshake timeout at `afm.nl` that reproduces under both user agents.

**Modules: choose what this install collects** (#48) — `config/regulators/` stays a complete catalogue; `config/modules.yaml` (yours, gitignored, with a committed `config/modules.example.yaml` alongside it in the `.env` / `.env.example` pattern) is your selection from it. A module is a regulator; a jurisdiction wildcard like `eu/*` expands to that jurisdiction and every descendant of it, so `eu/*` covers ESMA and every member state's authority. Resolution runs `defaults` → jurisdiction wildcard → explicit module id → `sources:`, narrower always winning, and the registry wins on `false` — anything `config/regulators/` marks `enabled: false` is never collected however explicitly you selected it, logged as a `WARNING` naming the module and source when it overrides something you asked for by name. Three loader states: a `modules.yaml` collects exactly what it selects; no file plus `REGRADAR_COLLECT_ALL=true` collects the whole registry; no file and no env var collects nothing and says so in one line, exiting 0 rather than looking like a crash. An invalid file (bad cron, unknown module id, unknown source label) is refused at startup with the offending entry named. `schedule:` and `on_enable:` are validated and carried through the schema but not yet acted on — the collector still runs one global `SCHEDULE`. **Existing installs need do nothing:** the first run after upgrading writes a `modules.yaml` containing `eu/*` and `gb/*`, which resolves to exactly the 33 regulators / 63 sources collected before — asserted against the real registry by `tests/test_modules.py`. What this buys is the thing the global coverage expansion would otherwise break: an EEA-only operator does not start downloading MAS circulars and NYDFS consent orders on their next upgrade. The cost, stated rather than averaged: query-time filtering is free to reverse, collection-time filtering is not — a module that was off for six months leaves a six-month hole, and many sources cannot be backfilled.

**Local upgrade from casp-radar to reg-radar completed** — the documented volume migration (`casp_radar_data` → `reg_radar_data`, backup dir moved to match) plus the v1→v2 data migration (reclassify `document_type`/`instrument` on both source-default and rule paths, legacy `content_tags` imported, `body_md` backfilled from `raw_content` for 18,603 pre-v2 items) were run end to end against the live local install, verified by matching item counts (20,715) before the old volume was deleted. The stale `.env` (still pointing at `casp_radar.db` and the old `regulators.yaml` path) was updated to the current v2 defaults. Found and fixed a gap the README's upgrade steps didn't cover: the volume-copy step preserves the old `casp_radar.db*` filenames, which the new `.env`'s `reg_radar.db` path wouldn't find, so the app would silently start against a fresh empty database — the DB files now get renamed inside the volume as an explicit step before first boot on the new volume. Local project folder renamed `casp-radar` → `reg-radar`; git worktree metadata repaired for the one active worktree (`v2`) that survived the move.

**Renamed casp-radar to regradar** (#3) — code-side rename only; no functional change. The database file (`casp_radar.db` → `regradar.db`), Docker volume (`casp_radar_data` → `regradar_data`), Litestream backup path, compose project name, default `USER_AGENT`, MCP server name, and the `skills/casp-radar-*` directories all move to the `regradar` name. Python packages (`collector`, `mcpserver`, `webui`), database tables, and the item id scheme are unchanged. Existing installs: see the README's "Upgrading from casp-radar" section for the volume migration steps — the compose file also accepts `DATA_VOLUME_NAME=casp_radar_data` as a stopgap so nobody boots against an empty database by surprise. The GitHub repository rename, name/trademark check, and the `2.0.0-alpha.1` tag are tracked separately and not part of this change.

**Canonical document format and original artefacts** (#4) — every item now has one canonical shape: a YAML-frontmatter Markdown document (id, title, source URL, regulator, jurisdiction and its ancestors, dates, labels, provenance, content hash) with the extracted body as Markdown, validated against a published JSON Schema in `docs/schema/`. `reg-radar render` writes that layout to disk, so the corpus can be dropped straight into a document management system or a note-taking vault without a bespoke exporter. The original fetched artefact (the HTML page or PDF as served) is stored alongside it under `ARTEFACTS_DIR` with its mime type and sha256, so a better extractor — or a legal team wanting the actual PDF — never has to re-fetch from the regulator. `scripts/reprocess_bodies.py --from-raw-content` re-derives Markdown bodies for items collected before this landed.

**Taxonomy, jurisdictions and a classification store with provenance** (#5) — flat tag lists are replaced by a configurable taxonomy (`config/taxonomy.yaml`): named axes, each with a cardinality and a controlled vocabulary of values with aliases and a per-axis minimum confidence. `document_type` (single-valued) and `instrument` (multi-valued) ship; the code hard-codes no axis name except `jurisdiction`, so adding one is a config change. Jurisdictions (`config/jurisdictions.yaml`) became a hierarchy with lower-case ids: every EU member state lists `eu` as a parent, so a filter on `fr` returns AMF *and* ESMA, and `UK` became `gb`. Labels are no longer written onto the item — every classification is a row recording who said it (`by`), how sure they were (`confidence`) and which taxonomy version was in force, with the highest-confidence live row above the threshold winning. A human correction is never overwritten by an automated pass. `reg-radar reclassify` re-applies source defaults or re-scores against the current config, and supersedes rows the config no longer supports rather than leaving them live. `get_taxonomy_tool` and `list_labels_tool` expose the vocabulary and what is actually in use.

**Rules engine, classification write interface and a classifier skill** (#6) — `config/rules.yaml` replaces v1's keyword alerts with a deterministic weighted rules engine: each entry scores one (axis, value) pair from regex matches across chosen fields, with a title multiplier and a global minimum confidence, and runs on every newly collected item. `/alerts` in the web UI became `/rules`, backed by that file, with validation against the taxonomy on save (`/alerts` redirects). The write side is now a real interface: `classify_item_tool`, `classify_items_tool` (up to 100 at once, every entry validated before anything is written, per-entry errors returned), `get_unclassified_tool` for paging the backlog one axis at a time, and `POST /api/items/{id}/classifications` for human corrections. `skills/regradar-classifier/` documents the loop so any MCP-connected agent can work the backlog — the repository holds no API keys and picks no vendor. `scripts/eval_classifier.py` scores live labels against a hand-labelled gold sample so accuracy is measured, not assumed.

**Profiles and activities** (#7) — a profile is a saved, named filter: jurisdictions (with `eu/*` selecting the EU and every member state), activities, instruments, excluded instruments, document types, regulators and languages, plus `include_unclassified` so items nothing has labelled yet stay visible by default. Activities (`config/activities.yaml`) let a profile say "I am a CASP" instead of listing instruments. The same profile applies identically in the web UI's picker, every MCP query tool's `profile` parameter, the JSON API, the exporter, the Atom feeds, webhooks and digests — one definition, one behaviour. Four templates ship in `config/profiles/`: `eu-casp`, `eu-bank`, `eu-emi`, `uk-equities-dealer`; your own profile is a YAML file passed by path.

**Source health, fixtures and nightly contract tests** (#9) — the failure that used to go unnoticed for weeks was a source returning HTTP 200 with markup the parser no longer matches. Every enabled source now has a captured last-known-good response under `tests/fixtures/sources/` and an offline contract test asserting the parser still produces the same shape from it. A nightly workflow re-fetches each source live, compares it against the fixture, and files (or closes) a GitHub issue per source, so selector drift surfaces on its own. A stall detector counts consecutive successful-but-empty runs per source, distinct from outright fetch failures, and surfaces stalled sources through `get_health_tool`, `list_regulators_tool` and the web UI's regulator panel. `scripts/capture_fixture.py` re-captures a fixture deliberately; nothing refreshes one automatically.

**Source adapter framework and per-jurisdiction registry split** (#10) — the three hard-coded source types inside one `fetch_source()` became a registry of adapter classes, each owning its own fetch and parse, sharing one post-fetch pipeline (extraction, snippet, language, id generation, artefact storage). Adding a fetch strategy is now a new file, not a new branch in shared code, and `sitemap`, `json_api` and a Playwright-backed `browser` adapter join `rss`/`scrape`/`page_watch`. The single 1,800-line `config/regulators.yaml` split into one file per jurisdiction under `config/regulators/`, validated against `config/jurisdictions.yaml` at startup, so adding a regulator is one config file, one fixture and one test, and a review diff names the jurisdiction it touches.

**Export, changes cursor, outbound feeds and webhooks** (#8) — the one change-stream primitive every downstream adapter now builds on: "everything that changed since cursor X" (an opaque `<updated_at>|<item_id>` cursor, id as tiebreak on equal timestamps). `get_changes_tool` and `GET /api/changes` both read it directly off `updated_at`, so a reclassification or human correction is now visible to a poller, not just a newly fetched item — `get_items_since_tool` is deprecated in favour of it (kept working, logs a warning). `reg-radar export --format markdown|jsonl --out <dir>` writes the canonical document layout (or JSONL), idempotent and cursor-tracked via a `.reg-radar-cursor` file in the output directory, with `--with-originals` to also copy artefacts. `GET /feeds/<profile>.atom` gives any RSS/Atom reader a per-profile feed. `config/webhooks.yaml` (unset by default) defines subscribers that get an HMAC-signed POST of new matching items after every collection run, with per-subscriber cursors, doubling-backoff retries, and a delivery log — one subscriber's failure never blocks another's.

**Published dataset** (#12) — a nightly GitHub Actions workflow publishes the full corpus as a GitHub release: a tarball of the canonical document tree plus `export.jsonl`, a `manifest.json` (schema and taxonomy version, `generated_at`, item count, per-regulator counts, excluded regulators, sha256), a moving `latest` tag and an immutable `dataset-YYYY-MM-DD` one. `reg-radar import-dataset <url|path>` loads it: sha256 verified before anything is written, a non-empty database refused without `--force`, items and classifications loaded straight from `export.jsonl` with their original provenance (`by`, `confidence`, `taxonomy_version`) intact, and a URL download bounded by `--timeout` and `--max-bytes`. What this saves a new install is the **historic backfill scripts** — the slow, FlareSolverr-throttled part — not the routine collection run, which reads each source's current feed pages either way; nothing filters fetches by date. The import records the manifest's `generated_at` as a sync cursor marking where the snapshot ends — a bookmark for change-stream consumers (`get_changes_tool`, `/api/changes`, a webhook subscriber) that want only post-import changes, never applied automatically. `import-dataset` prints it with ready-to-paste commands and `get_health_tool` reports it as `dataset_import`; `reg-radar export` still always writes the whole corpus into a fresh `--out`. Supporting changes: `reg-radar export` gained a repeatable `--format` (markdown and jsonl from one pass over one change set) and `--exclude-regulator-file`. A `NOTICE` file at the repository root records what is known about each enabled regulator's reuse terms — cited and quoted where the regulator states them, "unclear" otherwise, which is not the same as forbidden — and `config/dataset_exclusions.yaml` (empty for now) is where a regulator goes if its terms are found to forbid redistribution.

**Digests** (#13) — `config/digests.yaml` (opt-in, unset by default) defines scheduled digests: a profile, a cadence, and one or more delivery channels. Each digest renders everything that changed since its own stored cursor, grouped by jurisdiction then regulator, as plain text and HTML, and delivers by email (SMTP, with STARTTLS certificate and hostname verification), Telegram, or an HMAC-signed webhook. A digest's cursor advances only if every one of its channels succeeded, so a failed send is retried in full rather than silently skipped. The collector's own scheduler runs them — there is no second cron to configure — and `reg-radar digest --preview --profile <p>` renders one to stdout without sending anything, while `reg-radar digest --send --name <n>` can be driven from external cron instead.

**Batch classifier runner** (#14) — `reg-radar classify --provider <p> [--axis <a>] [--limit N]` works through the unclassified backlog without an agent in the loop. Providers are pluggable and their SDKs import lazily, so nothing is installed for a provider you don't use; the `command` provider shells out to any CLI that reads a prompt on stdin and writes text on stdout, which lets a subscription-backed tool drive classification instead of a metered key (check that vendor's terms before using it unattended). Every write carries `by: llm:<provider>/<model>` provenance, `--dry-run` classifies and prints without writing anything, and metered providers log token counts and an estimated cost per call priced from `config/llm_prices.yaml`; unmetered ones log as unmetered rather than fabricating a figure.

**Narrowed `document_type` source defaults to single-purpose feeds** — audited every `labels:` block across all 44 regulators in `config/regulators/*.yaml`. The v1→v2 tags migration (§4.7) had stamped `document_type: warning` at confidence 1.0 onto general/mixed feeds (`all_news`, `announcements`, `market_supervision`, `publications`, `news_and_warnings`, etc.) because v1's `warnings` tag was applied indiscriminately — since a source default at 1.0 outranks any rule or LLM label (§4.4), those mislabels were effectively permanent. Removed the `document_type` default from 26 sources that are not single-purpose for the value they carried, and corrected 4 sources that were single-purpose but mislabelled (e.g. BaFin's `press_pr` feed was tagged `warning` instead of `press_release`; DNB's and FCA's enforcement-notice feeds were tagged `warning` instead of `enforcement`). 12 sources kept their `document_type` default unchanged, where the feed is genuinely single-purpose (a `warnings`/`press_releases` label or equivalent, or a `page_watch` source). Operators should run `reg-radar reclassify --axis document_type` after upgrading to clear the stale `source_default` rows and let items fall back to rules/LLM classification.

**Fixes found against the real database** — bugs that only appeared once the whole pipeline ran over the live corpus rather than test fixtures. Classification writes stored `updated_at` in a different string format from the ORM's own writes, so the change cursor compared the two as text and could stop advancing, silently starving every change-stream consumer. `reg-radar reclassify` left rows live when the config no longer supported them, so a removed source default stayed as an effective label forever; it now supersedes them. Exports dropped `jurisdiction_ancestors` and `label_provenance` from every document, and wrote an empty body for any item collected before `body_md` existed — both are now derived on the export path, so a v1-upgraded database exports real text. The regulator-labels migration also now always runs its database jurisdiction rewrite, rather than skipping it when the YAML had nothing left to migrate.

**Final review fixes** — the whole-branch review before merge, applied in one pass. The README's volume-migration steps could destroy a live database if both options were followed in order: the old volume is now deleted only after the migration is verified, and the `DATA_VOLUME_NAME` override is removed explicitly first. Taxonomy and activities load at process startup, so a broken config kills the container at boot instead of turning every request into a 500. A `jurisdictions` filter passed without a taxonomy now raises instead of silently widening the query to the whole corpus. `/api/changes` and `reg-radar digest --preview` pass the taxonomy through, so their documents carry `jurisdiction_ancestors` and `label_provenance` like every other surface. `get_unclassified` derives bodies for v1-upgraded rows, so a classifier is not handed empty text. Classification writes against an item id that does not exist are rejected instead of recording an orphan row. The regulator panel takes country names from `config/jurisdictions.yaml` rather than a stale hand-maintained map, restoring search-by-country. Email delivery verifies the TLS certificate and hostname on STARTTLS. A webhook delivery failure can no longer make `--once` exit non-zero. The exporter reports only the items it actually wrote and warns about unparseable snapshot lines instead of dropping them quietly.

**Renamed regradar to reg-radar** — final naming pass: the interim name used throughout the v2 build (`regradar`) becomes the hyphenated **reg-radar** everywhere user-facing (Docker/compose project and volume names, the DB file, the MCP server name, the console script, the webhook signature header, the export cursor filename, dataset release/tarball names, skills directories, and docs). The Python package stays `regradar` (hyphens aren't valid in a module name) — `python -m regradar.cli`, `regradar/`, database table/column names, and the `regradar_schema` frontmatter key are unchanged. A `2.0.0-alpha.1` tag follows the merge of this change.

## 2026-07-04

**Historic backfill migrated to the new source/content tag split** — ran the migration script (built and dry-run tested yesterday) against the live database: 12,963 legacy items had their `source_tags` re-derived from the old `tags` column (blanket `casp`/`mica`/`aml`/`art`/`emt`/`dora` labels stripped) and `content_tags` freshly computed by re-running the keyword matcher against each item's real text — 600 items picked up a genuine, evidence-based content tag as a result. The final review of this migration script (before today's run) caught a Critical bug that would have silently wiped `source_tags` on every row the new collector had already tagged correctly — fixed and re-verified before the real run.

**MCP server security/correctness audit** — a full external review of `mcpserver/` produced 9 security/correctness findings and 7 improvement opportunities, all implemented:
- Fixed a timestamp-format bug in `get_warnings` that silently dropped items published on the cutoff day itself.
- Floored `limit` clamps across `search_items`, `get_recent`, and `get_run_log` — a negative limit could previously disable SQLite's `LIMIT` entirely, returning the whole table.
- Added a `limit` to `get_warnings` (previously unbounded) and offset-based pagination to `search_items`.
- Fixed `search_items` to use AND search semantics for multi-word queries (it was treating them as one exact phrase).
- The MCP server now opens the database read-only and fails fast if the database file is missing, instead of silently creating an empty schema.
- Enabled DNS-rebinding protection on the HTTP transport (FastMCP doesn't enable this automatically when binding `0.0.0.0`).
- Tool errors are now sanitized before reaching MCP clients — internal details (DB paths, SQL text) no longer leak into error messages.
- Fixed `Optional` type annotations across tool signatures.
- Five new MCP tools: `count_items_tool`, `get_month_facets_tool`, `list_tags_tool`, `get_items_since_tool` (a polling primitive), `get_health_tool` (collector freshness/readiness).
- All 11 tools now return structured content (dicts/lists) instead of JSON-encoded strings; `get_item_tool` gained a `max_content_chars` option to protect agent context windows.

**Production database corruption incident** — live testing surfaced real SQLite corruption in the `items` table (not the FTS search index, as first suspected). Root cause: the database very likely lived on a macOS Docker Desktop bind-mount, a known corruption risk for SQLite's WAL-mode locking. Recovery was attempted (an initial "fully recoverable" estimate didn't hold up under independent re-verification — the real number was ~83%), and the decision was made to scratch the corrupted database and let the collector rebuild it fresh, given the data is cheaply re-collected from public RSS/scrape sources.

**Infrastructure hardening**, shipped the same day to prevent a repeat:
- Moved the database off the macOS bind-mount onto a genuine Docker-managed named volume.
- Added Litestream as a continuous-backup sidecar, streaming the live database to a plain folder on the host disk — restore path verified end-to-end, not just configured.
- The collector now runs a full integrity check (`PRAGMA integrity_check`) at the start of every collection cycle and surfaces the result loudly through `get_health_tool`'s new `db_integrity` field, instead of corruption sitting silently undetected until a search happened to fail.
- Fixed a live regression the DNS-rebinding fix introduced: operators who remap the MCP server's published port (a documented workaround for port conflicts) got every request rejected with a 421 — the allowed-hosts list is now extensible via `MCP_EXTRA_ALLOWED_HOSTS`.
- Fixed `docker-compose.yml`: the `mcp` and `webui` services had never actually loaded `.env` — only `collector` had, so any environment-variable configuration for the other two services was silently a no-op.
- Fixed a dependency version conflict (`httpx`/`uvicorn` pins one version below what `mcp` requires) that blocked installing all three services' dependencies together for local testing.

## 2026-07-03

- Split the single `tags` column into `source_tags` (notice type, e.g. "warnings", "press_releases") and `content_tags` (topic, e.g. "mica", "travel-rule"), with a backfill migration and combined-by-default filtering across the MCP tools and web UI.
- Added a keyword-alerts system: `config/alerts.yaml` maps keywords to tags, applied automatically to items during collection; manageable from the web UI at `/alerts` without editing the file directly.
- Added a `page_watch` source type for tracking static pages (like ESMA's MiCA hub) via content-hash change detection, not just RSS/scrape.
- Added Malta FIAU and AMLA as tracked regulators.
- Fixed a date-parsing bug where `dayfirst=True` was corrupting already-ISO-formatted datetime strings.
- Routed RSS/Atom fetches through FlareSolverr when configured, for feeds behind Cloudflare.

## 2026-07-02

Initial build. Core collector (RSS/Atom + HTML scrape fetcher, SQLite storage, APScheduler-driven daily runs), MCP server (6 initial read-only tools), and web UI (browsable list/search/reader view) for EEA financial regulator news, warnings, and publications. Seeded `config/regulators.yaml` with full EEA coverage (30 member states + ESMA/EBA/EIOPA), plus dedicated scrapers for ESMA's document library, FCA publications, CNMV warnings (via PDF extraction), and MFSA (Malta). Added FTS5 full-text search with a LIKE fallback, paragraph-aware content chunking, and a disaster-recovery script for rebuilding the search index from source data. Hardened based on multiple external code reviews: SSRF protection on scrape-path redirects, non-root Docker users, loopback-only port binding, input validation/clamping on MCP tool parameters, and WAL mode with busy-timeout tuning to reduce lock contention.
