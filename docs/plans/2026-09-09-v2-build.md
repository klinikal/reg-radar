# RegRadar v2 build plan

Status: executing. Last updated: 2026-09-09.

This plan drives the v2 effort described in `docs/design/regradar-architecture.md` (the spec; binding authority) and the twelve issue files in `docs/issues/` (GitHub #3 to #14). Task numbers below are the GitHub issue numbers. Each task's requirements are its issue file, verbatim; this plan only adds build order, branch layout and the rulings taken where issues overlap or leave a gap.

## Branch layout

- `v2` is the integration branch, cut from `main`. Every task lands on `v2` via its own branch `feat/<N>-<slug>`, reviewed before merge. `v2` merges to `main` as one pull request once the whole effort is verified.
- Tasks in the same wave run in parallel on separate worktrees. Later waves branch from `v2` after the previous wave has merged.

| Wave | Tasks | Notes |
|---|---|---|
| 1 | 3 | Rename. Nothing runs alongside it. |
| 2 | 4, 5, 9 | Data format, taxonomy store, source health. |
| 3 | 7, 10 | Profiles, source adapters. |
| 4 | 6, 8 | Rules engine, export and change stream. |
| 5 | 12, 13, 14 | Dataset release, digests, batch classifier. |

Task 11 (coverage expansion) is a tracking parent with no code change and is out of scope for this build.

## Global Constraints

These bind every task.

- The spec is `docs/design/regradar-architecture.md`. If an implementation must deviate, change the doc in the same branch and say so in the report.
- Python 3.11. Tests: `pytest` from the repository root; the full suite must pass before a task reports done. Test output must be free of new warnings.
- Any new dependency is added to the relevant `*/requirements.txt` (pinned) and, once `pyproject.toml` exists, declared there too. No dependency for what a few lines of stdlib can do.
- Shared v2 code lives in the top-level `regradar/` package per spec section 6a. Subcommands attach to `regradar/cli.py`; no new standalone scripts for functionality the CLI is meant to own.
- Config over code: vocabularies, hierarchies, rules, activities and profiles live in YAML under `config/`. Code must not name any taxonomy axis except `jurisdiction`.
- Nothing silently disappears: unclassified items are visible by default; a stalled source is surfaced, not hidden.
- This repository is public. Nothing in code, docs, fixtures, commit messages or test data may contain personal names, local filesystem paths, agent names, credentials or tokens. Secrets are read from environment variables named in config, never stored in config.
- Commit messages follow Conventional Commits (`feat(scope): ...`, `fix: ...`, `docs: ...`, `test: ...`, `chore: ...`), imperative, lowercase, no trailing period. No `Co-Authored-By` trailers. No mention of any AI tool, model or vendor in commit messages or code comments.
- Stage files by explicit path. Never `git add -A` or `git add .`.
- Work only inside the assigned worktree. Never modify the main checkout, other worktrees, or anything outside the repository.
- No live calls to paid third-party APIs in tests or verification runs. Provider integrations are exercised with mocks or stub commands.
- When a task changes an MCP tool, HTTP route or CLI command, its README entry changes in the same branch.

## Task 3: Rename casp-radar to RegRadar

Requirements: `docs/issues/01-rename-to-regradar.md`. Wave 1. Branch `feat/3-rename-regradar`.

Rulings:
- Code-side rename only. The GitHub repository rename, the `2.0.0-alpha.1` tag and the trademark/name check are recorded as outstanding for the owner to execute at merge time; do not attempt them. The README clone URL and MCP examples use `klinikal/regradar` as specified so the branch is ready for that rename.
- The skill directories under `skills/` are renamed in this task. Copies installed elsewhere on an operator's machine are out of scope.
- CHANGELOG: add an entry under a new dated heading describing the rename and the upgrade path; do not claim the tag exists.

## Task 4: Canonical document format and original artefact storage

Requirements: `docs/issues/02-canonical-document-format-and-artefacts.md`. Wave 2. Branch `feat/4-document-format`.

Rulings:
- This task creates `regradar/__init__.py`, `regradar/cli.py` (argparse, subcommand registry), `regradar/document.py` and `pyproject.toml`. A parallel task creates `regradar/taxonomy.py`, `regradar/classification.py` and `regradar/reclassify.py`; do not create or reference those. Design `cli.py` so a later module registers a subcommand by exposing `add_subparser(subparsers)` and `run(args)`; document that convention in a module docstring.
- Body Markdown library: pick between `markdownify` and `html2text` as the issue says; the wrapper module is the only importer of the chosen library.
- The manual Obsidian rendering check with screenshots is replaced by an automated check that the rendered frontmatter is valid YAML with scalar and list properties only, plus the JSON Schema validation. A manual Obsidian open is done once on the integrated branch.
- `items.labels` is populated by Task 5; this task renders whatever the column holds and must tolerate the column being absent or empty.
- Open question on FTS: keep `raw_content` in the FTS index for now; record the recommendation in the report. Sharding stays by item id.

## Task 5: Taxonomy, jurisdictions and classification store with provenance

Requirements: `docs/issues/03-taxonomy-jurisdictions-classification-store.md`. Wave 2. Branch `feat/5-taxonomy-classification`.

Rulings:
- Runs in parallel with Task 4, which creates `regradar/cli.py`. Do not create `cli.py`. Put the `reclassify` command in `regradar/reclassify.py` exposing `add_subparser(subparsers)` and `run(args)`, and make it runnable as `python -m regradar.reclassify` for this branch's own tests. The integrator wires it into `cli.py` at merge.
- Create `regradar/__init__.py` as an empty file if it does not exist.
- Do not add or rename any `items` column other than `labels` and, if needed for the side table, nothing else; Task 4 owns `body_md`, `extractor`, `updated_at` and `item_artefacts`. If `updated_at` does not exist on this branch, add it with the same `_ensure_column` pattern and the same name, since both tasks need it; the integrator will reconcile.
- Labels storage: implement the `item_labels(item_id, axis, value)` side table as recommended, rebuilt by the materialisation function, and record the measurement against the JSON alternative in the report.
- `get_warnings_tool` is kept as an alias for `document_type=warning` for one release.
- The EEA is not a separate jurisdiction id; EEA-EFTA states list `eu` as parent.
- `ruamel.yaml` is a dependency of the migration script only; add it to `collector/requirements.txt` pinned.

## Task 9: Source health, fixtures, nightly contract tests and stall alerts

Requirements: `docs/issues/07-source-health-fixtures-nightly-contract-tests.md`. Wave 2. Branch `feat/9-source-health`.

Rulings:
- Runs in parallel with Tasks 4 and 5. In `collector/storage.py` touch only `SourceErrorRow` and its helpers; in `mcpserver/queries.py` touch only `get_health` and `list_regulators`; in `webui/` touch only the regulator panel. Add new functions at the end of the file they belong in.
- Fixture capture from live regulator sites is allowed for this task (it is the deliverable). Respect the existing per-domain throttle. If a source cannot be captured (network block, Cloudflare without FlareSolverr running), record it in the report with the reason and mark the contract test for that source as an expected failure with the reason in the marker; do not silently skip.
- `capture_fixture.py --all` stays a manual tool. Last-known-good fixtures refresh only on deliberate capture.

## Task 10: Source adapter framework and per-jurisdiction registry split

Requirements: `docs/issues/08-source-adapter-framework-registry-split.md`. Wave 3. Branch `feat/10-source-adapters`.

Rulings:
- Runs in parallel with Task 7, which touches `mcpserver/`, `webui/` and `regradar/profiles.py`. This task must not modify those beyond what `load_regulators()` callers strictly need.
- Task 9's `tests/test_source_fixtures.py` must keep passing; update it to call adapters instead of the old private parser functions if those move. Task 9's `capture_fixture.py` and nightly workflow share the fetch path; keep them working.
- Jurisdiction validation in the registry loader uses `regradar.taxonomy` from Task 5; do not write a second loader for `jurisdictions.yaml`.
- Task 4 added `raw_bytes` and `mime` to `Item`; `RawDocument` carries the same and the shared pipeline passes them through.
- The `browser` adapter's throttle: share the existing per-domain throttle. `json_api` dotted paths are sufficient.
- Playwright is heavy; install it in the collector image only, and keep the adapter importable without the browser binaries present so tests that do not use it still run.

## Task 6: Rules engine, classification write interface and LLM classifier skill

Requirements: `docs/issues/04-rules-engine-write-interface-llm-classifier-skill.md`. Wave 4. Branch `feat/6-rules-engine`.

Rulings:
- Runs in parallel with Task 8. Both add MCP tools to `mcpserver/server.py`, routes to `webui/app.py`, functions to `mcpserver/queries.py` and subcommands to `regradar/cli.py`. Append new tools, routes and functions at the end of the relevant file; do not reorder or reformat existing code.
- This task owns the web UI rules page: `/alerts` becomes `/rules` backed by `config/rules.yaml`, and `/alerts` redirects to `/rules`. Task 13 will not reimplement it.
- Rules run on insert via one call from the shared pipeline's classify step (Task 10's `collector/pipeline.py`).
- `get_unclassified_tool` gains `include_low_confidence` as recommended. Negative-evidence rules are not built.
- The gold sample under `tests/fixtures/classification/gold.csv` is hand-labelled from real items in the dataset; document how rows were chosen. No live LLM calls in tests.

## Task 8: Export, changes cursor, outbound feeds and webhooks

Requirements: `docs/issues/06-export-changes-cursor-feeds-webhooks.md`. Wave 4. Branch `feat/8-export-changes`.

Rulings:
- Runs in parallel with Task 6; see Task 6's file-region rule, which applies symmetrically.
- `regradar export` persists its own cursor file inside `--out` as recommended. Pagination only for `/api/changes`. Fixed `batch_size` per subscriber.
- Webhook subscriber cursors live in a small SQLite table, not a file, so Task 13's digest state can share the mechanism.
- Webhook delivery after a collector run is triggered from `collector/main.py` after `run_collection()` completes, guarded so a missing `config/webhooks.yaml` is a no-op.

## Task 12: Published dataset release

Requirements: `docs/issues/10-published-dataset-release.md`. Wave 5. Branch `feat/12-published-dataset`.

Rulings:
- The workflow file is written and validated for syntax; it cannot be exercised end to end in this build. The tarball, manifest and `import-dataset` paths are tested locally against a small database.
- `--exclude-regulator-file` is added to `regradar export` in this task.
- Provenance is included in the published dataset. Retention is not decided here.
- `NOTICE` rows default to "unclear" unless the reuse terms are stated on the regulator's site and cited by URL; no legal conclusions.

## Task 13: Digests and notifications

Requirements: `docs/issues/11-digests-and-notifications.md`. Wave 5. Branch `feat/13-digests`.

Rulings:
- Task 6 already moved the web UI alert page to `/rules` on `rules.yaml`. This task verifies the redirect and README, and does not build a second rules page.
- Digest state uses the same SQLite table mechanism as Task 8's webhook cursors.
- `send_empty: false` by default, configurable per digest. Numeric `chat_id` only. No digest UI.
- Scheduling: digests are run by the collector's existing scheduler process reading `config/digests.yaml` cron fields; no second scheduler.

## Task 14: Batch LLM classifier runner

Requirements: `docs/issues/12-batch-llm-classifier-runner.md`. Wave 5. Branch `feat/14-classify-runner`.

Rulings:
- Provider SDKs (`anthropic`, `openai`) are optional dependencies imported lazily inside their provider module, so the rest of the CLI works without them installed. Tests use mocked HTTP and a stub script for `command`.
- Failed validations are logged, not quarantined. One axis per call.
- The README documents the `command` provider's contract without recommending any specific vendor's subscription CLI for unattended use; note that operators must check their provider's terms.
