## Purpose

Every item is materialised as one Markdown file with YAML frontmatter, plus
the original artefact where one was fetched. This is the ingestion contract
for Obsidian, Notion, SharePoint, a vector store, or anything else that
reads files off disk.

## How it works

SQLite remains the query store. The exported Markdown files are a
projection of it, regenerated on demand by the exporter (see
[Export and Sync Contract](concept-export-sync-contract.md)).

Layout:

```
export/
  <jurisdiction>/<regulator_id>/<yyyy>/<yyyy-mm-dd>-<slug>-<id8>.md
originals/
  <id2>/<id>.<ext>          # content-addressed by item id, sharded on first two hex chars
```

`id8` is the first 8 hex characters of the item id. `slug` is the title,
lower-cased, ASCII-folded, non-alphanumerics collapsed to single hyphens,
truncated to 80 characters. Items with no `published_at` use `fetched_at`
for the path and set `date_inferred: true`.

Frontmatter is schema version 1 (`regradar_schema: 1`). It carries the item
id (sha256, unchanged from v1 `make_item_id`), regulator, jurisdiction and
its ancestors, title, dates (`published_at`, `fetched_at`, `updated_at`,
`date_inferred`), language, source fields, effective `labels` (after
precedence, see [Taxonomy and Classification](concept-taxonomy-classification.md)
section 4.4), `label_provenance` (one entry per effective value), a
`content_hash`, and an `original` block (path, mime, sha256, bytes) when an
artefact was fetched.

Rules on the frontmatter schema:

- Keys are stable. New keys may be added under schema version 1, removing
  or renaming a key bumps `regradar_schema`.
- `labels` holds effective values only. Axis names and values come from
  `config/taxonomy.yaml`. Single-valued axes hold a scalar, multi-valued
  axes hold a list, absent axes are omitted.
- Activities are never written to frontmatter, they are derived at filter
  time from `instrument` via `config/activities.yaml`.
- The body below the frontmatter is the cleaned document text as Markdown:
  headings preserved where the source had them, paragraphs separated by
  blank lines, tables as pipe tables where extraction allows, otherwise
  plain paragraphs. No HTML.
- An RSS snippet with no fetched body has the snippet as the body, followed
  by a single line `> Full text not collected. See source_url.`

The schema is validated against `regradar/schema/document-v1.json`.

The collector stores the original response for every item that has a body:
HTML as fetched (after FlareSolverr where used), PDF bytes as fetched.
Stored under `originals/` on disk, referenced from an `item_artefacts`
table (`item_id`, `path`, `mime`, `sha256`, `bytes`, `fetched_at`). Size caps
stay as they are (`MAX_PDF_DOWNLOAD_BYTES`). Originals are excluded from
the published dataset by default and included with a flag.

## Inputs

Items already stored in SQLite, plus any fetched original artefact bytes
(HTML or PDF), plus `config/taxonomy.yaml` for axis names and values.

## Outputs and side effects

Markdown files under `export/<jurisdiction>/<regulator_id>/<yyyy>/`, and
original artefact files under `originals/<id2>/<id>.<ext>`.

## How to run or invoke

The files are generated by the exporter, not written directly. See
[Exporter](cli-exporter.md).

## How to test

Schema conformance is checked against `regradar/schema/document-v1.json`.
See [Document](component-document.md) for the runnable check.

## Boundaries

Removing or renaming a frontmatter key must bump `regradar_schema`, it must
never happen silently under the same schema version. Labels written to
frontmatter must be effective (post-precedence) values only, never raw
per-classifier rows. Activities must never be written to frontmatter, they
are always derived at filter time.
